## Открытые

### GUI (Windows) нестабильность: туннель рвётся и не закрывается (в дереве, НЕ СОБИРАЛОСЬ)
Симптомы: туннель обрывается; после этого «Disconnect» не отрабатывает, либо маршруты/DNS
остаются в TUN и машина без связи. Консольный `AetherLink.Client` при этом работает стабильнее.
Причины (по коду):
1. **Pump умирал молча.** Поток pump выходит при ошибке записи/чтения, но `Client` держит
   `up=true`, статус `Up`, маршрут по умолчанию остаётся в TUN ⇒ интернета нет, GUI показывает «Up».
   Фикс: `status()` отдаёт `pump_alive`; GUI переводит в `Lost` и сам делает teardown.
2. **Закрытие могло зависнуть навсегда.** Запись в мёртвый сокет блокировалась без таймаута,
   `stop()` ждал `join` под глобальным мьютексом FFI ⇒ `down` не возвращался.
   Фикс: `WRITE_TIMEOUT` 10с + `shutdown(Both)` сокета перед `join` в `PumpHandle::stop`.
3. **Подключение могло повиснуть.** TLS/AUTH handshake без таймаута, держал мьютекс FFI ⇒
   и Connect, и Disconnect висят. Фикс: `HANDSHAKE_TIMEOUT` 15с на сокет до pump.
4. **Гонки в GUI.** Двойной клик Connect создавал второй клиент и второй state (первый
   туннель потом не откатывался); Down во время Up мог поднять `IsUp` уже после Down;
   `Changed` писал в UI-биндинги из фоновых потоков. Фикс: `_opGate` в `TunnelService`,
   флаг `_busy` в VM, `Dispatcher.UIThread.Post`.
5. **Нет восстановления после аварии.** GUI не вызывал `aether_client_force_cleanup`, а
   `lifecycle::up` отказывает при наличии state-файла ⇒ после краша/убийства процесса
   Connect не работает, сеть указывает в мёртвый TUN. Фикс: кнопка «Restore network».
6. **Выход без teardown.** Kill из диспетчера, sign-out и shutdown Windows не вызывали `Down`.
   Фикс: `AppDomain.ProcessExit` и `SystemEvents.SessionEnding` → `Shutdown()`.
7. **TCP connect без таймаута.** `lifecycle::connect` звал `TcpStream::connect` — при
   дропающем SYN сервере `up` висел до ~2 минут (OS retry budget), держа глобальный мьютекс
   FFI: Connect крутился «вечно», Disconnect не мог вклиниться. Фикс: `CONNECT_TIMEOUT` 10с
   (`connect_timeout` по каждому резолвленному адресу, первый успешный wins).
8. **Disconnect во время Connect молча игнорировался.** `_busy` → return, кнопка не меняла
   подпись ⇒ «при дисконнекте всё зависает». Фикс: подпись «Cancel», teardown дожидается
   `up` (теперь bounded таймаутами) и снимает туннель сразу после его возврата.
9. **Shutdown зависал на UI thread.** `window.Closing` вызывал `_tunnel.Down()` синхронно
   без таймаута — окно не закрывалось, пока down ждал in-flight up/pump join. Фикс:
   `Shutdown(timeout)` на Task.Run (10с при закрытии окна, 2с в ProcessExit/SessionEnding);
   невыполненный teardown восстанавливается авто-ретраем по state-файлу (п.10).
10. **Stale state-файл блокировал Connect навсегда.** После краша/kill `up` падал с
    «stale state file», GUI не восстанавливал сеть сам ⇒ «не поднимается туннель». Фикс:
    ядро возвращает спецкод `StaleState` (-11, `ClientError::StaleState`), GUI автоматически
    делает force_cleanup и один retry Connect.
11. **`aether_last_error` портил кучу.** `CString::into_raw` утекал на каждый вызов, а .NET
    для `string`-return освобождал Rust-память через CoTaskMemFree ⇒ heap corruption,
    случайные крэши/зависания GUI. Фикс: thread-local **NUL-терминированный** буфер
    (у Rust-`String` нет NUL, поэтому первый вариант с `String::as_ptr()` читался CStr за
    границу аллокации — ловится тестом на точное совпадение сообщения), C# читает через
    `Marshal.PtrToStringUTF8` (GUI + CLI + Server).
12. **Клиенты копились в FFI-карте** (не было `aether_client_free`). Фикс: free после down
    и после failed up (GUI + CLI); drop клиента сам дожимает pump/TUN.
13. **Autostart (`--minimized`) игнорировался** — окно всё равно показывалось. Фикс: старт
    свёрнутым в трей.

Не сделано (следующий шаг, нужны решения по протоколу):
- **keepalive_s не используется.** Клиент не шлёт Ping, поэтому idle-сессия через NAT может
  умереть тихо. Сервер не отвечает на Ping (`accept.rs`, `FrameType::Ping => continue`), поэтому
  dead-peer детекции при простое нет (сработает таймаут записи при трафике). Нужно: клиент шлёт
  зашифрованный Ping с непустым телом (пустой фрейм сервер читает как EOF и закрывает сессию,
  `read` в пустой буфер даёт `Ok(0)`), сервер эхо-отвечает Ping. Требует тестов на протокол.
- FFI держит глобальный мьютекс `HANDLES` на всё время `aether_client_up` — теперь bounded:
  connect 10с + handshake 15с + netsh retries; per-client lock вместо глобального —
  отдельная задача (сейчас один клиент на процесс, выигрыш малый).
- Сборка и тесты не запускались (в песочнице нет cargo и dotnet). Перед мержем:
  `cargo test --workspace`, `cargo clippy -- -D warnings`, `dotnet build` GUI, живой прогон
  на Windows: обрыв сети во время туннеля, kill процесса, Restore network.

## Открытые

### 0m. Аплоад 0.00, вторая и главная причина: сплит-TCP без управления потоком (в дереве, гейты НЕ прогонялись)
0l убрал потери на сервере, но живой спидтест всё равно 0.00 — потому что потеря была
следствием, а не причиной. Настоящая причина в архитектуре сплит-TCP:

1. Клиент подтверждал байты приложению **в момент приёма** из TUN (self-ack из 0i) и
   всегда объявлял окно 65535 (`build_tcp_packet_full` захардкодил его). Приложение
   говорит с нашим фейковым стеком по петле: RTT ~1мс, окно 64КБ ⇒ оно стартует
   **сотнями Мбит/с**.
2. Туннель (аплоад 10-20 Мбит/с) столько не вывозит. Излишек где-то кончается: раньше
   молча падал в `try_send` на сервере, теперь честно закрывает поток (`close_stream`).
3. **И это не лечится ретрансмитом**: приложение шлёт повтор, а клиент его отбрасывает
   как дубль (`seg.seq != expected` → drop). Байты потеряны навсегда, поток мертв ⇒
   в отчёте ровно 0.00. Именно поэтому «маленькие» запросы (рукопожатия, GET) ходят,
   а bulk-закачка умирает на первой же перегрузке.

Фикс — управление потоком на.upload-пути:
- **ACK только после реальной записи.** `DataPump` больше не подтверждает байты при
  приёме: подтверждение уходит из `flush_acks()` после того, как кадр записан в сокет
  (`frames_written()`). Приложение разгоняется ровно настолько, насколько туннель
  реально забирает.
- **Окно настоящее, а не константа.** В каждом ACK поле `window` = остаток буфера
  закачки (`PENDING_FRAMES_MAX = 256` кадров ≈ 0.4МБ); новый билдер
  `build_tcp_packet_window`, в `TcpSegment` добавлено поле `window`. Переполнение буфера
  больше не «молча выбросить», а «сказать приложению остановиться» — без RTO-шторма 0g.
- **Приём с контролем**: если буфер полон, сегмент роняется **без подтверждения** и без
  продвижения `client_bytes`, поэтому повтор от приложения принимается (это ровно тот
  seq, который мы ждём) — поток восстанавливается, а не умирает. Как только место
  появляется, троттлёным потокам уходит window update.

Диагностика (что искать в логе с `AETHERLINK_DEBUG=1`):
- `pump: tcp id=N ... upload buffer full (N pending), holding` — буфер полон (норма при
  закачке, приложение притормаживает);
- `pump: tcp id=N out-of-order/drop (seq X vs expected Y)` — **до фикса** эти строки
  шли лавиной на закачке: это приложение долбится ретрансмитами, которые мы сами и
  отбрасывали;
- `tunnel: data id=N relay stalled past 1s, closing stream` (сервер) — перегрузка
  доходила до сервера.

Осталось известное ограничение: запись в сокет блокирующая, поэтому на饱和ной закачке
один поток может подтормаживать остальные (HOL) — отдельная задача.

### 0l. Аплоад 0.00: байты терялись молча, FIN убивал ответ, id кончались (в дереве, гейты НЕ прогонялись)
Симптом: 20 Мбит/с вниз, 0.00 вверх. Разбор пути вверх (TUN → DataPump → mux →
tunnel_loop → stream_worker → relay) дал не одну дыру, а несколько; каждая сама по себе
обнуляет аплоад:
1. `forward_tcp` клал payload в очередь воркера через `try_send`: на полной очереди
   байты молча выбрасывались. Приложение эти байты уже подтвердило своему стеку
   (сплит-TCP), ретрансмита не будет — поток встаёт насмерть. Фикс: блокирующая отправка
   с ожиданием до `SEND_HOLD` (1с) — backpressure уходит через туннель обратно в стек
   приложения (оно просто перестаёт получать ACK); если воркер всё равно утонул, поток
   закрывается сигналом, а не молчанием.
2. Конец потока не доходил до клиента: воркер снимался с учёта, но пир висел на сокете до
   своего таймаута. Фикс: пустой DATA-кадр = сигнал конца потока (пустых payload от живого
   отправителя не бывает — чистые ACK отфильтрованы). Сервер шлёт его при EOF/сбое релея и
   при недоставленном payload; клиент отвечает на него FIN приложению (мёртвый аплоад лучше
   зависшего).
3. Клиентский FIN убивал поток до ответа: `forget_tcp` сносил flow сразу, поэтому ответ на
   запрос с `Connection: close` доставить было некому; mux-id при этом не освобождался вообще
   — после ~4096 потоков новые не открывались ("too many streams"), туннель немел для новых
   соединений. Фикс: half-close (FIN → FIN-ACK приложению + пустой DATA в relay, flow живёт
   для входящих), `mux.close(id)` при забывании flow, реaper (half-closed 120с, UDP 300с,
   раз в секунду), UDP-потоки перестали течь (каждый DNS-запрос держал id до конца сессии),
   `alloc_id` пропускает занятые id, OPEN на сервере сбрасывает replay-окно и снимает
   устаревшего воркера.
4. Один плохой пакет из TUN или один stray DATA без маршрута убивал pump/сессию целиком.
   Фикс: ошибка drain'а TUN больше не fatal (пауза 10мс и дальше), stray DATA и сбой open —
   `continue` (пропуск потока), а не `break` всей сессии.
Плюс квант чтения: пока TUN produces, сокет читается с таймаутом 1мс вместо 10мс (иначе
TUN→wire упирался в 10мс на кадр — потолок ~50 Мбит/с при окне 64КБ).
TEMP-DIAG(upload) из f97ddf2 удалён: счётчики `sealed_total`/`got_reply` и серверные
`debug_log` убраны, grep по TEMP-DIAG чист.
Тесты (RED→GREEN): client — FIN объявляет half-close и ответ всё ещё доставляется, закрытие
пира FIN'ит сокет приложения, 4200 потоков подряд не исчерпывают id; mux — закрытый id
возвращается в оборот; server — 320КБ аплоада доходят целиком и закрываются, недоставленный
relay закрывает поток, а не вешает его; живой поток после мёртвого отвечает.
Гейты: НЕ ПРОГОНЯЛИСЬ — в рабочей песочнице нет Rust toolchain (нет cargo/rustc,
static.rust-lang.org и crates.io недоступны). Нужны `cargo fmt --check`,
`cargo clippy --all-targets -- -D warnings`, `cargo test --workspace` и живой замер на VPS.

### 0i. Аплоад стоял: ACK только piggyback — self-ack (в дереве)

следующие пейлоады ждут сокет в очереди FIFO; UDP без очереди).
Тест: bursty_stream — 1 коннект, байты по порядку. Гейты: 227/227.

### 0d. Флейк bind_serve под параллельной нагрузкой — ИСПРАВЛЕН
Два теста падали на server.bind() только в полном параллельном прогоне:
tempdir по nanos сталкивался между потоками, concurrently записанные
cert.pem читались partial. Фикс: pid+thread+counter в имени (только тест). Причина: tunnel_loop — один поток, каждый новый мёртвый таргет стоит 5с dial-таймаута; кулдаун спасал от повторов, но не от первого касания. Фикс: RelayPool (32 воркера), главный цикл только читает/сиалит/пишет. Теория «сервер виснет» — закрыта, он просто тормозил. Подтверждение: verify_client.ps1 — DNS OK + HTTP OK (HTML) против VPS, всё в бюджете.


1. **Петля egress на совмещённом стенде (клиент+сервер на одном хосте).**
   Маршруты клиента (`/1` через TUN) захватывают и собственные сокеты
   сервера: запрос уходит в TUN → памп → снова серверу. Для DNS закрыто
   direct-правилами апстримов; для произвольного TCP на одном хосте
   решения нет по построению. Лечится топологией: тестировать против VPS.
   Статус: задокументировано как ограничение стенда, не баг.
2. **Серийные стойла event-loop сервера.** Каждый первый дайл в мёртвую
   цель — 5с, каждый UDP-релей в тишину — 2с, всё серийно. Частично закрыто:
   dead-target cooldown 30с, пропуск multicast, dial-only на пустых DATA,
   fallback апстримов. Структурно лечится конкурентным релеем (воркеры/
   nonblocking dial) — отдельная задача, не начата.
3. **Модель запрос-ответ вместо стриминга TCP.** Пустой SYN DATA дайлит и
   ждёт чтения, которого не будет; полный дуплекс/продвижение окна не
   реализованы. Покрыто тестами поведения, живой curl — следующий пруф.
4. **Флейк `bind_serve` KeyMismatch в общем прогоне.** Изолированно 5/5
   зелёных; падает только под параллельной нагрузкой workspace. Причина
   в окружении (порты/серты тестов), не в коде tun/пампа.
5. **DPI провайдера подменяет DNS-ответы локально** (чужие A-записи).
   На работу туннеля не влияет (байты идут как есть), мешает только
   интерпретации ручных проверок. Эталон — ответы через VPS-апстрим.
6. **Падения VPS-сервера SIGSEGV (2 случая).** Локальный soak (120 TCP +
   60 UDP, дубли OPEN, тампер) краш не воспроизвёл — shape трафика
   невиновен. Следующий шаг: дебаг на VPS через drop-in
   (`AETHERLINK_DEBUG=1`) + живой батч; либо окружение (контейнер/.NET).
7. **IPv6 обходит v4-туннель.** `curl` без `-4` уходит напрямую по IPv6.
   Известное ограничение; проверки pu только с `-4`.
8. **Ctrl+C через pipe может не доходить до процесса.** Штатный путь —
   команда `down`; плюс auto-down хуки в хосте. `kill -9` покрывается
   журналом `UpState` + `cleanup`.
