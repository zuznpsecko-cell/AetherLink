# Live Issues (рабочий журнал живых прогонов)

Актуальные известные проблемы живых прогонов и их статус. Обновляется по
итогам каждого батча. Детали фаз — `PLAN_FINAL_TDD.md`, счётчики — ниже
в `STATUS.md`.

## Открытые

### 0l. Аплоад 0.00: байты терялись молча, FIN убивал ответ, id кончались (в дереве, гейты НЕ прогонялись)
Симптом: 20 Мбит/с вниз, 0.00 вверх. Разбор пути вверх (TUN → DataPump → mux →
tunnel_loop → stream_worker → relay) дал не одну дыру, а несколько; каждая сама по себе
обнуляет аплоад:
1. `forward_tcp` клал payload в очередь воркера через `try_send`: на полной очереди
   байты молча выбрасывались. Приложение эти байты уже подтвердило своему стеку
   (сплит-TCP), ретрансмита не будет — поток встаёт насмерть. Фикс: блокирующая отправка
   с ожиданием до `SEND_HOLD` (1с) — backpressure уходит через туннель обратно в стек
   приложения (оно просто перестаёт получать ACK); если воркер всё равно утонул, поток
   закрывается сигналом, а не молчанием.
2. Конец потока не доходил до клиента: воркер снимался с учёта, но пир висел на сокете до
   своего таймаута. Фикс: пустой DATA-кадр = сигнал конца потока (пустых payload от живого
   отправителя не бывает — чистые ACK отфильтрованы). Сервер шлёт его при EOF/сбое релея и
   при недоставленном payload; клиент отвечает на него FIN приложению (мёртвый аплоад лучше
   зависшего).
3. Клиентский FIN убивал поток до ответа: `forget_tcp` сносил flow сразу, поэтому ответ на
   запрос с `Connection: close` доставить было некому; mux-id при этом не освобождался вообще
   — после ~4096 потоков новые не открывались ("too many streams"), туннель немел для новых
   соединений. Фикс: half-close (FIN → FIN-ACK приложению + пустой DATA в relay, flow живёт
   для входящих), `mux.close(id)` при забывании flow, реaper (half-closed 120с, UDP 300с,
   раз в секунду), UDP-потоки перестали течь (каждый DNS-запрос держал id до конца сессии),
   `alloc_id` пропускает занятые id, OPEN на сервере сбрасывает replay-окно и снимает
   устаревшего воркера.
4. Один плохой пакет из TUN или один stray DATA без маршрута убивал pump/сессию целиком.
   Фикс: ошибка drain'а TUN больше не fatal (пауза 10мс и дальше), stray DATA и сбой open —
   `continue` (пропуск потока), а не `break` всей сессии.
Плюс квант чтения: пока TUN produces, сокет читается с таймаутом 1мс вместо 10мс (иначе
TUN→wire упирался в 10мс на кадр — потолок ~50 Мбит/с при окне 64КБ).
TEMP-DIAG(upload) из f97ddf2 удалён: счётчики `sealed_total`/`got_reply` и серверные
`debug_log` убраны, grep по TEMP-DIAG чист.
Тесты (RED→GREEN): client — FIN объявляет half-close и ответ всё ещё доставляется, закрытие
пира FIN'ит сокет приложения, 4200 потоков подряд не исчерпывают id; mux — закрытый id
возвращается в оборот; server — 320КБ аплоада доходят целиком и закрываются, недоставленный
relay закрывает поток, а не вешает его; живой поток после мёртвого отвечает.
Гейты: НЕ ПРОГОНЯЛИСЬ — в рабочей песочнице нет Rust toolchain (нет cargo/rustc,
static.rust-lang.org и crates.io недоступны). Нужны `cargo fmt --check`,
`cargo clippy --all-targets -- -D warnings`, `cargo test --workspace` и живой замер на VPS.

### 0. Серийный event-loop сервера — ИСПРАВЛЕН И ПОДТВЕРЖДЁН LIVE
Pcap + журнал показали: сервер отвечал через 21с после SYN (id=55 в 14:25:57), клиент сдавался на 10-й секунде и рвал сессию (RST) — ответ приходил в мёртвый сокет (Broken pipe).

### 0b. ERR_SSL_PROTOCOL_ERROR в браузере — НАЙДЕН КОРЕНЬ (фикс в дереве)
Туннель идеален (egress=VPS), но браузер рвал TLS-handshake: relay читал
ОДИН раз и возвращал первый сегмент, ServerHello+certs (~4-6КБ) приезжали
обрезанными. curl везло (влезало в сегмент). Фикс: exchange_stream —
write + drain до тишины (idle 300мс, cap 1МБ); keep-alive сокеты
переиспользуются. Пул: воркеры 32 + очередь 256 (burst 180 потоков без
shed; shed TCP DATA = stall поверх client-dedup, только для флуда).
Гейты: 224/224, clippy чист. Нужен редеплой VPS + живой речек браузера.

### 0c. Насос умирал от одного большого ответа — ИСПРАВЛЕНО (в дереве)
Живой прогон: ответ 189КБ одним DATA-кадром -> клиентский read_sealed
отверг как absurd frame length (лимит 66559) и ЗАВЕРШИЛ pump-поток:
туннель немел целиком (curl-таймауты, SSL-ошибки). Фикс: сервер режет
ответы на чанки <=64КБ (sealed <=65552), клиентский fail-closed остаётся
как защита от тампера. Тест: oversized_reply 200КБ цел + loop жив.
Гейты: 226/226 (дважды подряд, стабильно).

### 0k. Кулдаун травил живые цели после одного чиха (в дереве)
Спидтест-аплоад показал 0.00: первый же медленный dial к :8080 маркировал
цель мёртвой на 30с, все ретраи (весь короткий тест) скипались в пустоту.
В эпоху дуплекса серийных стойл нет (воркер терпит), кулдауну нечего
защищать. Фикс: DialFail — refused (точно мёртв) кулдаунится, timeout и
прочее считается transient и не маркируется. Гейты: 234/234.

### 0j. Nagle душил мелкие записи (в дереве)
58КБ/с детерминированы до +-0.006% — так умеют только таймеры/полисеры.
Кодовых квантов на 25мс не осталось; зато Nagle был включён ВЕЗДЕ (ни
одного set_nodelay в дереве): записи по 1.4КБ с flush сидели в очереди
Нагла в ожидании delayed ACK. Фикс: TCP_NODELAY на клиентском, серверном
и relay-сокетах. Гейты: 233/233. Ждёт живого замера.

### 0i. Аплоад стоял: ACK только piggyback — self-ack (в дереве)
Bulk POST полз 3КБ/с и рвался: чистые TCP-ACK цели kernel-to-kernel до нас
не доходят, а наши ACK уходили только на ответах. Без ответов приложение
встаёт past cwnd, ретрансмиты дропаются как дубли, прогресс ноль. Фикс:
клиент инжектит чистый ACK сразу после пересылки каждого DATA
(подтверждаем приём в релей — сплит-TCP семантика). Бонус: убирает самый
жирный timing-сигнал прокси (ACK возвращаются мгновенно, как напрямую).
Гейты: 231/231. Нужен только клиент (сервер не менялся).

### 0h. Дуплекс вместо запрос-ответ (в дереве)
58с на страницу даже с адаптивным idle: каждый exchange серийно, linger,
простои. Переписано: воркер на TCP-поток (свой сокет от dial до FIN,
пишет по мере прибытия, читает с квантом 50мс, отчёты по мере прибытия);
UDP остался на пуле (датаграммам pairing подходит). Убраны linger,
очереди, батчинг, warm. Guard-тест: медленный поток не душит быстрый.
Burst-тест переведён на последовательный диалог (write-then-read всего
сразу — дедлок по заполнению буферов, как у любого клиента без чтения).
Гейты: 230/230.

### 0g. Скорость: RTO-шторм от 200мс idle на каждый запрос — ЧАСТИЧНО (в дереве)
Страница грузилась минутами: каждый exchange ждал 200мс тишины, ответы
позже RTO (~300мс) -> 2900 ретрансмитов за прогон, каждый запрос в
несколько RTO-циклов. Фикс: адаптивный idle (200мс только на свежем dial
для сборки handshake, 25мс на переиспользуемом). Следующий шаг при
недостаточности: полный дуплекс вместо запрос-ответ. Гейты: 230/230.

### 0f. Таймаут чтения рвал сессию посреди кадра — ИСПРАВЛЕНО (в дереве)
READ_TIMEOUT на сокете (50мс сервер / 200мс клиент) превращал любую паузу
в теле кадра в смерть сессии: сервер писал body eof, closing, клиент получал
FIN (10054). Тело большого кадра — десятки TCP-сегментов, пауза почти
гарантирована. Фикс: чтение тела с отслеживанием позиции, таймауты лишь
продолжают (лимит 30с, потом fail-closed). Заголовки как раньше (24Б, один
сегмент). Тесты: dribbled body e2e + unit. Гейты: 229/229.

### 0e. Частичный hello висел 5с и травил поток — ИСПРАВЛЕНО (в дереве)
Сериализация держала один сокет, но первый job уносил лишь первый кусок
hello (536Б) и ждал ответа 5с, который невозможен без остатка; потом fail,
кулдаун, очередь скипнута. Фикс: батчинг очереди (linger 50мс собирает
пачку, один job пишет всё сразу), квант чтения 200->50мс, cap очереди
256/поток. Гейты: 227/227.

### 0d. Поток рвался на параллельные dials — ИСПРАВЛЕНО (в дереве)
Браузерный ClientHello (~2КБ, 4 TUN-пакета подряд) уходил 4 отдельными
dial'ами: каждый воркер открывал свой сокет и писал кусок hello — Google
не собирал hello из кусков и молчал, 5с таймаут, кулдаун на 30с, все
ретраи скипнуты, браузер показывает CIPHER_MISMATCH. (Прямой коннект с VPS
работал: TCP_OK + 404 за 50мс — сеть чиста, виноват был наш fan-out.)
Фикс: сериализация по потоку (busy+pending: максимум 1 job на stream,
следующие пейлоады ждут сокет в очереди FIFO; UDP без очереди).
Тест: bursty_stream — 1 коннект, байты по порядку. Гейты: 227/227.

### 0d. Флейк bind_serve под параллельной нагрузкой — ИСПРАВЛЕН
Два теста падали на server.bind() только в полном параллельном прогоне:
tempdir по nanos сталкивался между потоками, concurrently записанные
cert.pem читались partial. Фикс: pid+thread+counter в имени (только тест). Причина: tunnel_loop — один поток, каждый новый мёртвый таргет стоит 5с dial-таймаута; кулдаун спасал от повторов, но не от первого касания. Фикс: RelayPool (32 воркера), главный цикл только читает/сиалит/пишет. Теория «сервер виснет» — закрыта, он просто тормозил. Подтверждение: verify_client.ps1 — DNS OK + HTTP OK (HTML) против VPS, всё в бюджете.


1. **Петля egress на совмещённом стенде (клиент+сервер на одном хосте).**
   Маршруты клиента (`/1` через TUN) захватывают и собственные сокеты
   сервера: запрос уходит в TUN → памп → снова серверу. Для DNS закрыто
   direct-правилами апстримов; для произвольного TCP на одном хосте
   решения нет по построению. Лечится топологией: тестировать против VPS.
   Статус: задокументировано как ограничение стенда, не баг.
2. **Серийные стойла event-loop сервера.** Каждый первый дайл в мёртвую
   цель — 5с, каждый UDP-релей в тишину — 2с, всё серийно. Частично закрыто:
   dead-target cooldown 30с, пропуск multicast, dial-only на пустых DATA,
   fallback апстримов. Структурно лечится конкурентным релеем (воркеры/
   nonblocking dial) — отдельная задача, не начата.
3. **Модель запрос-ответ вместо стриминга TCP.** Пустой SYN DATA дайлит и
   ждёт чтения, которого не будет; полный дуплекс/продвижение окна не
   реализованы. Покрыто тестами поведения, живой curl — следующий пруф.
4. **Флейк `bind_serve` KeyMismatch в общем прогоне.** Изолированно 5/5
   зелёных; падает только под параллельной нагрузкой workspace. Причина
   в окружении (порты/серты тестов), не в коде tun/пампа.
5. **DPI провайдера подменяет DNS-ответы локально** (чужие A-записи).
   На работу туннеля не влияет (байты идут как есть), мешает только
   интерпретации ручных проверок. Эталон — ответы через VPS-апстрим.
6. **Падения VPS-сервера SIGSEGV (2 случая).** Локальный soak (120 TCP +
   60 UDP, дубли OPEN, тампер) краш не воспроизвёл — shape трафика
   невиновен. Следующий шаг: дебаг на VPS через drop-in
   (`AETHERLINK_DEBUG=1`) + живой батч; либо окружение (контейнер/.NET).
7. **IPv6 обходит v4-туннель.** `curl` без `-4` уходит напрямую по IPv6.
   Известное ограничение; проверки pu только с `-4`.
8. **Ctrl+C через pipe может не доходить до процесса.** Штатный путь —
   команда `down`; плюс auto-down хуки в хосте. `kill -9` покрывается
   журналом `UpState` + `cleanup`.

## Закрытые живыми прогонами

- `wintun open missed` при живом адаптере; friendly-name рассинхрон.
- OEM/cp866-декод `ipconfig`, суффикс `(Основной)`, тип в русских заголовках.
- Новорождённый wintun disabled; `none`-gateway как синтаксическая ошибка.
- Метрика default 30 вместо 5 → захват через `/1` + привязка `if`.
- Сессия wintun умирала в конце выражения; платформа пересоздавалась.
- Пустой `force_cleanup` (только удалял файл) → реальный реплей.
- DNS-тампер рвал весь цикл; тампер flow → скип flow.
- Multicast-шторм вешал цикл на 5с каждый.
- Дубли `up`, stale-DNS в снапшоте, корневые секции конфига вне `client:`.
- Рассинхрон таблиц flow при ошибках send/seal → паника (фикс `09d7fc4`).
- Редеплый поверх живого бинаря (ETXTBSY) → стоп сервиса в скрипте.
- Ручной `netsh set address`/`dnsservers` ходит мимо (состав команд в коде).
- Потерянный `stderr` curl в батчах (`2>&1` обязателен).
- Рассинхрон логов разных эпох → метки времени в дебаге, один батч = один вывод.

## Правила живых прогонов (выученные)

- V2RayN выкл, Telegram/браузер закрыть, иначе шум ×100 флоу.
- Один батч = один вывод; файлы логов читать из репо, не из вставки.
- Сервер и клиент перезапускать из свежих DLL каждый раз.
- `state.json` + таблица маршрутов проверяются до и после.
- Никогда не убивать окно A без последующего `down`/`cleanup`.
